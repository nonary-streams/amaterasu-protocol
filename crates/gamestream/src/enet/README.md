# GameStream ENet wire codec

`decode(bytes, &Limits)` and `encode(&Datagram, &Limits)` implement the
uncompressed, checksum-free ENet wire profile used by Moonlight's control stream.
The codec owns no socket, timers, retransmission queue, endpoint authorization,
or fragment reassembly. Those responsibilities belong to the peer engine and
managed transport. Successful parsing does not establish peer identity or permission
to send a reply.

The types preserve the 12-bit peer ID, two-bit session ID, optional 16-bit sent time,
channel, reliable sequence, command flags and complete command fields. All wire
integers use network byte order except `connect_id: [u8; 4]`: ENet deliberately
copies that identifier without endian conversion, so it must be echoed byte for
byte. Initial CONNECT session IDs may be 255; verified sessions must be 0..=3.
Peer ID 4095 is the unconnected sentinel. Control commands use channel 255;
message channels must be below the configured channel count. Acknowledgements can
refer to either a message channel or the control channel.

Supported commands are ACKNOWLEDGE, CONNECT, VERIFY_CONNECT, DISCONNECT, PING,
SEND_RELIABLE, SEND_UNRELIABLE, SEND_FRAGMENT, SEND_UNSEQUENCED, BANDWIDTH_LIMIT,
THROTTLE_CONFIGURE, and SEND_UNRELIABLE_FRAGMENT. Payload bytes are preserved
without interpretation. The codec rejects reserved command bits, unknown command
numbers, incompatible command flags, invalid control/message channels, and
acknowledgement-requesting commands without a datagram sent-time field. It accepts
the reliable, unsequenced and unflagged DISCONNECT forms.

Fragment metadata is checked without allocating the advertised message length:
nonzero count/length, bounded count and total size, valid index, nonempty payload,
offset/end within the total, and first/last boundary consistency. Reliable fragment
sequence numbers must equal the starting sequence plus fragment index modulo
65536. The peer engine must still handle overlaps, inconsistent fragments across
datagrams, duplicate delivery, windows, and reassembly deadlines.

## Bounds and unsupported profiles

`Limits` defaults to MTU 4096, 48 channels, 1024 fragments and 65536 message bytes.
Callers may lower these limits; maximum supported message size is 128 KiB so the
peer engine can explicitly admit the 65539-byte encrypted control envelope. MTU
must be 576..=4096, channels 1..=255, and fragment count 1..=1024. Each UDP datagram
contains at most 32 commands. Payload allocation while parsing is limited to
bytes actually present in that bounded datagram, not declared fragment totals.
Serialization validates before allocating output and rejects data exceeding MTU.
No partial command list or truncated payload is returned on failure.

The compressed-header bit produces `UnsupportedCompression`. Checksums have no
on-wire presence flag, so the caller must supply the negotiated profile:
`Limits.checksum=true` produces `UnsupportedChecksum` on both encoding and decoding.
The checksum-free parser cannot identify arbitrary checksum bytes masquerading as
commands. It does not silently support ENet compression or checksum negotiation.
The bounds and channel/handshake checks are an explicit GameStream profile, not a
promise to accept every permissive behavior of general ENet implementations.

Primary Moonlight uses 48 control channels. Its pinned ENet fork defaults to a
900-byte MTU, unlike other ENet distributions. CONNECT may advertise a different
supported MTU, which the peer engine negotiates against its configured maximum.
The codec preserves bandwidth and throttle fields; it does not implement their
congestion-control effects or decide an amplification budget.

## Independent verification

Primary sources inspected locally:

- [Moonlight ControlStream.c](https://github.com/moonlight-stream/moonlight-common-c/blob/874ac9548f1bd6f095ef2b435c42cdde460e7821/src/ControlStream.c): ENet setup and control use.
- [ENet protocol.h](https://github.com/cgutman/enet/blob/aca87840b57f045a1f7f9299e4b1b9b8e2a5e2f1/include/enet/protocol.h): packet layouts, command IDs and flags.
- [ENet host.c](https://github.com/cgutman/enet/blob/aca87840b57f045a1f7f9299e4b1b9b8e2a5e2f1/host.c) and [protocol.c](https://github.com/cgutman/enet/blob/aca87840b57f045a1f7f9299e4b1b9b8e2a5e2f1/protocol.c): session, connect-ID and command semantics.

Pinned sibling behavior was inspected without copying or translating production
source. The Rust codec uses explicit byte operations, with no packed-struct casts,
unsafe code or external dependencies. The original C test bridge includes the
actual upstream headers and links its actual peer implementation from an external
checkout; upstream C code is not embedded in the Rust library.

`fixtures.txt` contains twelve packets generated by those packed C definitions.
Tests assert decoded field values, byte-identical serialization, every truncated
prefix, malformed flags/channels/headers, oversized datagrams/command counts,
fragment amplification bounds, and wrapping sequences. The explicit oracle test
regenerates the fixture file and compares it exactly; it passed using the pinned
checkout. Ordinary tests consume the committed fixture without requiring C tools.

To rebuild the oracle from an existing checkout, without downloads:

```sh
crates/gamestream/src/enet/build-oracle.sh /path/to/moonlight-enet /tmp/amaterasu-enet-oracle
AMATERASU_ENET_ORACLE=/tmp/amaterasu-enet-oracle cargo test -p amaterasu-gamestream enet::tests -- --include-ignored
```

The build helper checks ENet commit `aca87840b57f045a1f7f9299e4b1b9b8e2a5e2f1`
and a clean tracked tree. Recorded SHA-256 values:

- `include/enet/protocol.h`: `e135dfbd0fd2cf60d9b5f92cc3ed7ce4f6fa2e46e5281915380437dc3c255159`
- `protocol.c`: `08072968184824810e0aebf3120b8811bc3fc6334f49dfa18967ac473e14b82f`

The oracle also has `client PORT`: a real upstream ENet client connects to loopback
with connect data 0x11223344, exchanges reliable channel-0 and fragmented channel-7
messages with an echoing server, then disconnects with data 0x55667788. It has a
five-second total deadline. The peer engine owns the corresponding interoperability
test and its evidence. Codec fixtures alone do not establish reliable delivery,
connection security, complete GameStream control semantics or streaming readiness.
